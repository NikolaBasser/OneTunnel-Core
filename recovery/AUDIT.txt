OneTunnel offline WFP recovery audit
Reviewed: 2026-10-26

Incident result

The confirmed orphan belonged to an isolated Phase 4 test identity, not the installed production owner. Its provider key was D6E3D9D9-3BA8-55E5-532F-4C821DB7929D. A read-only inventory showed 23 related filters and one sublayer. The operator removed that exact provider through the offline recovery path; the follow-up inventory was empty, DNS resolution was reported working, and HTTPS 204/200 checks passed. No later network tests were run. No user SID or private filesystem path is recorded here. The provider-key derivation is SHA-256("OneTunnel.WFP.v1/" + owner SID + "/provider"), with the first 16 digest bytes converted to a Windows GUID. The identified test owner was synthetic; the production owner was not implicated.

The failed active-canary guard recorded outcome `worker-identity-unavailable` before its deadline. In `artifacts/.roadmap-active-canary/guard.go (runWatchdog)`, the SYSTEM watchdog reads the acknowledged worker identity and checks PID, process creation time, image path, and process state. If `exactWorkerAlive` cannot inspect or verify that exact worker (exactWorkerAlive/inspectWorker), it writes the generic outcome and returns instead of continuing until the deadline (worker-identity-unavailable branch). The evidence does not retain the underlying Win32 error, so the precise inspection failure cannot be determined. The subsequent watchdog restart failed at `watchdog.check-fresh-root`: `runWatchdog` refuses to adopt a pre-existing unique runtime root (watchdog.check-fresh-root branch), which the first worker had created. That guard prevented unsafe recovery against an unknown root, but the early identity-check exit left the test policy behind. These events explain the canary failure; they do not prove a legacy production-root mismatch. The legacy C# root mismatch remains a separate unverified hypothesis.

WFP callsites and ownership

- Current first-party persistent policy: `internal/platform/wfp_windows.go:104-116` derives provider/sublayer/filter keys and the 32-byte normalized-root fingerprint, then opens the local WFP engine. `:188-202` writes the recovery marker and starts a transaction. `:218-229` adds the provider and sublayer with persistent flag `1`; `:231-305` adds persistent filters with provider/sublayer links, allow/block action, weight, and conditions; `:306-308` commits. `:310-369` removes only the derived provider family after checking the 32-byte root fingerprint, using a transaction. `internal/platform/runtime_windows.go:384-407` deliberately preserves journal and WFP state on service shutdown; explicit disconnect/recovery paths remove it at `:1085-1104` and `:1125-1178`.
- Emergency utility: `internal/platform/emergency_wfp_windows.go:32-69` enumerates provider, sublayer, and filter batches and frees each returned WFP allocation. `:71-140` builds provider-linked inventory; `:143-177` checks the exact provider name, known filter labels, supported layers, persistence, action, weight, and condition counts. It displays the 32-byte root fingerprint, but does not compare it to a filesystem-derived expected value: the directory may no longer exist. The README correctly describes this as metadata identification, not authentication against a local administrator able to forge WFP metadata. `:196-268` parses the selected provider, validates the full selection inside a WFP transaction, deletes only linked filters, sublayers, and provider in that order, and aborts on failure. All-provider removal is one transaction.
- CLI and SCM: `cmd/onetunnel-recover/main_windows.go:16-49` defaults to read-only inventory and validates a supplied GUID before any SCM operation. Mutations require elevation (`:34-36`); recovery checks the `OneTunnelCore` service state (`:85-124`) and stops it only when `--stop-service` was explicitly passed. The CLI inventories again after removal and verifies selected providers are absent (`:68-80`). It does not construct Runtime, load profiles or journals, issue network requests, or modify routes, DNS, proxy, or Windows Firewall policy outside the validated OneTunnel provider objects.
- Historical first-party source: commit `2db1b00`, `tests/LegacyCore/KillSwitch.cs:10-18` documents intentional persistence and uses the same owner-derived key family plus a root-path SHA-256. `:40-57` writes a marker and transactionally adds persistent provider, sublayer, and filters; `:59-80` installs the four-layer deny/permit rules and commits. `:87-117` gates ordinary removal on the marker, checks provider root data, then deletes the known filter range, sublayer, and provider transactionally. This is historical source, not the cause established by the isolated canary.
- Vendor WFP callsites: cached `sing-tun` `tun_windows.go:188-215` opens a dynamic WFP session and adds an unowned sublayer; `:224-364` adds interface/DNS filters; `:561-563` closes the session. Cached WireGuard Windows `tunnel/firewall/blocker.go:26-47` opens a dynamic session; `:50-99` creates random provider/sublayer GUIDs; `:104-189` installs filters and closes the session on failure or disable. AmneziaWG Windows uses the corresponding pattern in its versioned `tunnel/firewall/blocker.go:26-47,50-101,104-188`. Their objects are session-scoped rather than marked persistent, so they are not the reboot-surviving provider identified above. No separate Xray WFP-add callsite was found in the resolved module sources reviewed.

Recovery package

`build-recovery.ps1:1-10,14-26` requires a new or empty output directory, rejects output paths containing the source tree and reparse-point ancestors, and builds Windows amd64/arm64 binaries with CGO disabled. `-Offline` disables Go proxy and checksum-database access. `:26-37` packages the launcher, instructions, Go and linked-module licenses, build metadata, hashes, and ZIP. The default binary dependency list was limited to Go, go-winio, x/net, x/sys, and x/text; it does not include embedded proxy/TUN engines.

`recovery/Start-Recovery.cmd:1-2` invokes the PowerShell launcher. `recovery/Start-Recovery.ps1:3-12` requests elevation and selects the architecture binary; `:14-31` logs inventory, then runs `--recover-all --stop-service`, clearly warning that OneTunnel protection is removed and the service is stopped. Failure preserves the log and does not issue a global firewall reset. `recovery/RECOVERY.txt:17-38` documents the metadata-only identity limit, direct-traffic consequence, and operations the tool does not perform.

Review boundary

This was a source/package review only. No recovery executable, WFP mutation, service stop, or network test was run during this review. Existing platform tests (`internal/platform/emergency_wfp_windows_test.go:9-74`) cover ABI layouts, metadata predicates, selection, and the synthetic provider-key derivation; they do not exercise the host WFP database.

Archived Go copy: the monorepo GoCore/internal/platform/wfp_windows.go contains the same first-party persistent add/delete implementation; it is not a separate provider family. No original application protection semantics were changed by this emergency utility. Packet-path benchmarks and profiling are not applicable to this one-shot administrative tool.
